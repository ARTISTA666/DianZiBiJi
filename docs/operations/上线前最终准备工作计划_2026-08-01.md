## 1. 执行摘要

本项目已经具备较完整的产品闭环、自动化测试框架、发布门禁、备份恢复脚本和生产安全配置校验，工程基础明显强于普通原型。但当前工作区不是可发布候选版，现有证据也不能证明当前代码可上线。

必须先完成以下五类阻断项：

1. 修复并验证当前 Rust 笔记版本写入中的数据语义破坏风险。
2. 整理本次规划开始时已有的 87 个工作区状态条目，冻结唯一、干净、可追溯的发布提交。
3. 统一 Rust 生产 schema、legacy Alembic、OpenAPI 和前端契约的唯一权威来源。
4. 在冻结提交上重新生成全量 CI、E2E、重启恢复、性能、生产配置、TLS、备份恢复和证据清单。
5. 完成真实用户验收、DeepSeek 外发边界决策、中文/英文业务 OCR 验收以及 Go/No-Go 独立复审。

在这些条件全部满足前，不应把“本机能运行”“某次测试通过”或“旧证据曾通过”表述为“生产可上线”。

### 1.1 建议周期

建议为本轮预留 **至少 7–10 个工作日**。其中 4 小时长稳测试、真实用户验收、真实 TLS、异地加密备份恢复和独立复审不能压缩为一次本机冒烟测试。

如果上线还要同时启动论文确认性人工评审，应额外预留外部题集冻结和两名独立评价人的协调时间。

## 2. 范围与假设

### 2.1 本计划纳入范围

- full-system/ 下的 Next.js 前端、Rust/Axum 生产后端、PostgreSQL 16 + pgvector、宿主持久文件存储。
- 文件上传、OCR、知识图谱、本地检索、DeepSeek 生成、固定任务智能体、五方法对照实验和盲评。
- Docker Compose 单机部署、Nginx TLS 入口、监控、日志、备份、恢复、发布和回滚。
- 生产上线门禁及与论文确认性人工评审相关的独立门禁。

### 2.2 明确排除

- 工作区根目录中的论文 Word/PDF/渲染产物不作为应用部署内容。
- ponytail/ 是独立项目，不纳入本次上线。
- 本计划不代替代码修复、测试执行、安全法律意见或实际部署审批。

### 2.3 当前默认假设

- 目标是小规模科研团队使用的生产环境，采用单主机 Docker Compose + Nginx。
- PostgreSQL 与上传目录需要形成一致恢复点。
- 浏览器通过真实 HTTPS 域名同源访问 /api。
- DeepSeek 是唯一外部生成服务；本地哈希嵌入不向外发送文本。
- 若实际目标只是答辩演示而非真实用户生产使用，仍应保留数据完整性、权限、密钥和备份底线；可以通过书面风险接受缩减长稳与灾备范围，但不得声称生产成熟。

## 3. 项目理解

### 3.1 真实生产架构

~~~mermaid
flowchart LR
    U["用户浏览器"] --> N["Nginx / HTTPS / 同源 /api"]
    N --> F["Next.js 16 前端"]
    N --> B["Rust 1.88 + Axum 生产后端"]
    B --> P["PostgreSQL 16 + pgvector"]
    B --> S["宿主持久文件目录"]
    B --> O["Poppler + Tesseract OCR"]
    B --> D["DeepSeek HTTPS 接口"]
    B --> M["/health /ready /metrics"]
~~~

生产后端是 backend/src/ 中的 Rust 服务。backend/app/ 下的 FastAPI 只保留为 legacy/dev-only 参考和部分脚本探针，不参与生产运行。发布验收必须以 Rust 行为为准，不能用 Python 测试数量替代 Rust 生产覆盖。

### 3.2 三条核心价值流

1. **实验笔记链路**：创建 v1 → 编辑生成新版本 → 提交 → 审核退回/批准 → 批准版本锁定 → 自动抽取知识图谱 → 全程审计。
2. **资料知识链路**：上传 → 资料审核 → 图片 OCR → 审核人校对确认 → 文件哈希绑定 → 分块与本地向量入库 → 混合检索/图谱增强问答。
3. **论文验证链路**：冻结问题与参数 → 五方法异步运行 → 强杀后标记 interrupted → 显式续跑 → 方法隐藏的独立双人盲评 → 证据清单与完成门禁。

### 3.3 权限模型

系统存在六类全局角色：super_admin、pi、group_leader、project_owner、reviewer、member。真正的项目能力还取决于 owner 身份以及 can_read、can_write、can_review、can_evaluate、can_manage 五个项目权限标志。

必须特别说明：

- 非敏感项目的 PI 可读取；敏感项目不会自动向 PI 开放。
- 小组成员关系不自动继承项目权限。
- 独立评价人应只有 can_evaluate=true，不能读取、写入、审核或管理项目原始内容。
- 前端隐藏按钮不是权限控制，所有越权验收必须直接访问 URL 和 API。

### 3.4 AI 与数据边界

- 嵌入由本地 rust-hash-512-v1 完成，不需要外部模型。
- RAG 会把检索片段、文件名、图谱关系和问题拼入提示词发送给 DeepSeek。
- 智能体会把已批准笔记、文件和图谱摘要发送给 DeepSeek。
- 当前 is_sensitive 项目没有单独的第三方外发开关或脱敏门。
- DeepSeek 失败时系统会显式报错并记录，不生成模拟答案。
- 图片只有在 OCR 已被审核确认且文件哈希仍匹配时才能进入 RAG，这是应保留的关键数据质量门。

### 4.3 不能当作放行证据的现有结果

- 2026-08-01 本地 Playwright 报告显示 6/6、重启恢复成功、90/90 load smoke 成功，但报告未绑定干净 revision。
- 该 Playwright 报告生成于 15:53，而当前 user-journeys.spec.ts 在 17:02 又加入了“多角色 AI 资料、图谱、问答与报告协作”旅程，因此报告还没有覆盖当前 7 条测试。
- 旧 validation-results 主要验证 Python/Alembic schema，不能证明当前 Rust 启动迁移和 84 个 live operation。
- 旧 E2E 使用固定 LLM stub，只证明接口和业务流程，不证明真实 DeepSeek 的准确性、可追溯性或可用性。
- OCR 历史结果含英文手稿和乌克兰语压力集，不能代表生产默认 chi_sim+eng 对中文/英文仪器截图、标签和实验记录的业务效果。

### 4.4 已确认的产品/实现错配

| 主题 | 当前错配 | 上线前决策 |

## 11. 回滚计划

### 11.1 立即回滚触发器

发生以下任一情况，Release Commander 应在 15 分钟内决定回滚，不等待“再观察一下”：

- 任何认证绕过、跨项目读取/写入、独立评价人看到原始内容。
- 笔记版本、审批、文件、OCR 或 RAG 数据出现丢失、重复转义或不一致。
- /ready 连续 10 分钟不能恢复。
- 5xx 比例持续超过 1%，或 p95 持续超过 2000ms 且影响关键旅程。
- 数据库迁移失败、约束缺失、HNSW 异常或存储目录不可写。
- 新版本产生无法解释的大量审计、OCR、DeepSeek 或磁盘负载。
- secret 暴露、证书异常、错误域名/CORS、生产仍开启演示数据。
- 监控和备份都不可用，无法确认系统真实状态。

### 11.2 三层回滚

| 层级 | 适用条件 | 计划 |
| --- | --- | --- |
| L1 应用回滚 | schema 向后兼容，尚无数据语义变化 | 切回前一镜像 digest，保持 DB/storage，不解除监控 |
| L2 前向修复 | 问题局部、数据未损坏、可在维护窗口安全修复 | 保持停写，独立验证 patch，新 RC 全量重跑后再部署 |
| L3 数据恢复 | schema/数据已被破坏或无法证明兼容 | 保持应用停止，使用 T-75m 一致性备份替换 DB + storage，验证 /ready 后再开放 |

当前迁移包含 bigint、HNSW、实验租约和潜在 lock_version 分歧，因此不能默认 L1 一定安全。DB-04 必须为每个 RC 明确可回滚性。

### 11.3 回滚目标

- 决策时间：≤15 分钟。
- 应用回滚：目标 ≤30 分钟。
- 全量恢复：目标 ≤4 小时。
- 回滚后必须保留失败版本日志、request ID、schema fingerprint、证据和备份，不在事故中清理。

P0 必须关闭；P1 默认必须关闭，只有业务负责人、安全和独立 Reviewer 共同书面接受后才可例外；P2 必须有 owner 和日期。

## 15. 上线后计划

### T+0 至 T+2 小时

- 集中观察 /ready、5xx、p95、in-flight、DB 连接、磁盘、容器重启、DeepSeek 失败率。
- 每 30 分钟执行角色 smoke，不重复写入生产测试垃圾。
- 验证 request ID 可从用户错误追到后端日志和审计。
- 保持 Release Commander、Verifier 和 Rollback Owner 在线。

### T+1 天

- 核对首日用户、项目、笔记、审批、文件、OCR、RAG 和审计数量。
- 检查每日备份已加密异地复制，并做非破坏性可读性检查。
- 复盘告警噪音、DeepSeek 成本、OCR 资源占用和用户阻塞。
- 关闭或轮换 bootstrap 管理员凭据；确认无演示账号/数据。

### T+3 天

- 汇总用户问题、错误率、p95、磁盘增长、备份大小和恢复预估。
- 对 P2 债务重新排序，任何安全/数据类问题立即升级。

### T+7 天

- 执行最新异地备份的隔离恢复抽检。
- 召开上线复盘，确认是否结束 hypercare。
- 更新容量基线、运行手册、权限说明、风险登记册。
- 决定是否进入 G4 正式确认性人工评审；未过 G4 时只能继续内部试评。

## 16. 本计划的完成定义

本计划本身完成，不代表系统已经上线就绪。真正完成必须同时满足：

1. 所有 Blocking 项关闭；
2. G0–G3 全部通过并签字；
3. 冻结 RC、生产实际运行版本与证据清单属于同一 revision；
4. 回滚与恢复在独立环境中被实际验证；
5. 上线窗口按本计划执行并进入 T+7 复盘。

在此之前，统一对外口径应为：

> 系统具备完整工程基础和可复跑门禁，但当前发布候选尚未冻结，生产外部证据与用户验收仍待完成，因此暂不具备正式上线条件。
