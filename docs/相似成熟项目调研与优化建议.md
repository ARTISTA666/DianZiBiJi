# 相似成熟项目调研与优化建议

生成日期：2026-07-08

## 一、调研目的

本报告围绕当前“智能电子实验笔记系统”的论文主线进行外部成熟项目调研。当前系统的核心定位不是普通 CRUD 型 ELN，而是：

```text
项目级权限约束
  -> 实验笔记与资料审核
  -> 已审核记录进入可信知识层
  -> 实验知识图谱抽取
  -> 普通 RAG 与图谱增强 RAG 成对对照
  -> 问答日志、来源、评价与审计追溯
```

因此，外部项目不只按“是否也是 ELN”筛选，而按以下四类成熟能力筛选：

1. ELN 核心记录与审计：实验记录、附件、版本、签名、导出、API。
2. 科研数据/样本管理：样本、实验、项目、数据集、流程和权限。
3. RAG/AI 应用平台：知识库、检索、工作流、Agent、可观测记录。
4. 论文可支撑性：能否作为“已有成熟系统/开源实践/设计依据”的实体案例。

## 三、重点项目拆解

### 1. eLabFTW

仓库地址：https://github.com/elabftw/elabftw

定位：开源电子实验记录本，兼具 ELN 与轻量 LIMS 属性。其仓库描述明确强调面向 research labs 的开源 ELN。

与当前系统的关系：

- 本项目早期已经设计过 eLabFTW Companion PoC，说明“以成熟 ELN 为核心，自研智能层/知识层”的架构路线是可成立的。
- eLabFTW 可作为论文中“成熟 ELN 系统”的主要实体对照，用来说明传统 ELN 已能解决记录、附件、权限、导出等基础问题。
- 当前 `full-system` 的创新点应避免表述为“从零实现 ELN 就是创新”，而应表述为“在项目级权限和审核约束下构建可信知识层，并验证 KG-RAG 效果”。

可借鉴优化：

- 保留当前系统的“审核通过后才进入图谱/知识库”机制，并在论文中与 eLabFTW 的实验记录可信边界相呼应。
- 为笔记、附件、资料、问答日志补充统一 `source_id/source_url/source_type`，形成可追溯链。
- 将 eLabFTW Import/Adapter 作为未来扩展：当前系统可导入外部 ELN 记录，避免论文显得封闭。

### 2. openBIS

官方地址：https://openbis.ch/

定位：面向科研的 FAIR 数据管理解决方案，覆盖科研数据、元数据、项目/实验/样本等组织问题。

与当前系统的关系：

- openBIS 更偏科研数据管理平台，不只是实验笔记编辑器。
- 其价值在于强调“实验对象、样本、数据集、元数据”的统一管理，这与当前系统的知识图谱实体建模高度相关。
- 当前系统的图谱实体包括项目、笔记、用户、附件、实验类型、试剂、仪器、样本、结果，可借鉴 openBIS 的元数据思想继续规范化。

可借鉴优化：

- 为试剂、仪器、样本、结果增加结构化字段字典，减少纯文本规则抽取的不稳定性。
- 增加“项目数据冻结/实验批次冻结”机制，支撑论文对照实验的可复现性。
- 在论文第 4 章中说明：本系统没有构建完整科研数据平台，而是在 ELN 场景中抽取轻量实验知识图谱。

### 3. Chemotion ELN

仓库地址：https://github.com/ComPlat/chemotion_ELN

定位：化学领域电子实验记录本和研究数据管理系统，仓库主题包含 `eln`、`rdm`、`smart-lab`、`fair-data`。

与当前系统的关系：

- Chemotion 的成熟点不是通用笔记，而是将化学实验对象结构化，例如样品、反应、分析数据等。
- 对当前生物医学课题组系统而言，它可以作为“领域结构化模板”的对照案例。

可借鉴优化：

- 将 PCR、Western Blot、细胞培养、CCK-8 等模板从页面字段提升为可版本化的模板定义。
- 每类模板配置推荐实体抽取字段，例如 PCR 模板优先抽取样本、引物、酶、退火温度、扩增结果。
- 在论文中把 Chemotion 用作“领域 ELN 通过结构化对象提升数据复用”的案例。

### 4. SENAITE

仓库地址：https://github.com/senaite/senaite.core

定位：企业级开源实验室信息管理系统（LIMS）。

与当前系统的关系：

- SENAITE 的强项在样本流程、实验室业务流转、权限和审核。
- 当前系统虽然不是完整 LIMS，但有资料审核、笔记审批、项目成员权限、审计日志，可以借鉴 LIMS 的流程严谨性。

可借鉴优化：

- 为“实验笔记审批”和“资料入库审核”增加状态机说明：draft/submitted/approved/returned/archived/voided。
- 审计日志增加操作前后关键字段摘要，便于证明“关键业务操作可追溯”。
- 对资料审核进入 RAG 知识库增加失败重试和人工复核状态。

### 5. LabKey Server

仓库地址：https://github.com/LabKey/server

官方地址：https://www.labkey.org/

定位：面向生物医学研究的数据平台。官方站点运行页面暴露出 Assay、Experiment、Inventory、Search、API、Audit、FileContent 等模块能力。

与当前系统的关系：

- LabKey 是“科研数据门户 + 模块化数据管理”的成熟案例。
- 当前系统的单页工作台已经包含项目、笔记、资料、搜索、知识图谱、AI、审计，可在论文中与“研究数据门户”思路对齐。

可借鉴优化：

- 将前端“大工作台”在论文中拆解为模块：实验记录、资料库、知识图谱、AI 知识库、审计日志。
- 后续工程上可拆分前端模块，避免单一页面过大影响维护。
- 增加 API 级别的权限测试矩阵，证明项目隔离不是前端隐藏，而是后端强制。

### 6. Dify

仓库地址：https://github.com/langgenius/dify

定位：面向 Agentic workflow development 的生产级平台，主题覆盖 RAG、workflow、agent、low-code、MCP 等。

与当前系统的关系：

- 当前项目早期设计中考虑过 Dify，后续 `full-system` 已转向本地 pgvector + DeepSeek 的可复现实验链路。
- Dify 可作为“成熟 AI/RAG 应用编排平台”的外部参照，而不是必须依赖的运行底座。

可借鉴优化：

- 保留模型、提示词版本、检索参数、语料哈希、耗时和 token 用量记录，这一点比直接调用通用平台更适合论文复现。
- 可增加“外部 RAG 平台适配接口”章节，说明系统可替换为 Dify/RAGFlow，但论文实验使用本地可控链路。
- 智能生成任务应继续限定为固定任务型，不夸大为自主 Agent。

### 7. RAGFlow

仓库地址：https://github.com/infiniflow/ragflow

定位：开源 RAG 引擎，强调 RAG 与 Agent 能力结合，为 LLM 构建上下文层。

与当前系统的关系：

- 当前系统的创新点是“图谱增强上下文 + 普通 RAG 成对对照”，与 RAGFlow 的上下文层思路相近。
- RAGFlow 可支撑论文中“RAG 系统已成为成熟工程方向，但面向实验记录的权限约束与图谱增强仍需场景化设计”的论述。

可借鉴优化：

- 将文档解析、分块、召回、重排、生成、日志记录拆成清晰流水线。
- 对每个回答记录 `retrieval_context`、`graph_context`、`generation_context`，便于第 7 章分析。
- 对无图谱命中的问题显式记录“降级为普通 RAG”，当前系统已有该方向，应在论文中强化。

### 8. Kadi4Mat / Kadi 生态

相关线索：

- Kadi4Mat API client：https://github.com/fcskit/kadi4mat-client
- Kadi4Mat RAG chatbot：https://github.com/ValeMetzger/kadi4mat_rag_system_chatbot
- Kadi4Mat 笔记同步生态：https://github.com/fcskit/obsidian-kadi4mat-sync

定位：科研数据基础设施及其 API/笔记同步/RAG 周边生态。

与当前系统的关系：

- 该生态说明“科研数据平台 + 外部笔记工具 + RAG 助手”的组合正在形成。
- 对本论文最有价值的是支撑“科研数据管理系统与 RAG 助手结合具有现实工程背景”。

可借鉴优化：

- 为系统提供稳定 REST API 和导出格式，方便未来接入外部笔记或数据平台。
- 对 AI 问答接口增加批量实验 API，减少人工页面操作，提高论文实验复现性。
- 明确区分“知识库资料”和“实验笔记”两类语料的权限与审核规则。

## 五、论文中可使用的写法

### 相关系统章节

可以将成熟项目分为三类描述：

1. 电子实验记录本与实验室信息管理系统：eLabFTW、Chemotion ELN、SENAITE。
2. 科研数据管理平台：openBIS、LabKey Server、Kadi4Mat。
3. RAG 与智能应用平台：Dify、RAGFlow。

建议表述：

> 现有 ELN/LIMS 系统已经较好支持实验记录、样本管理、附件、权限与审计等基础能力，但面向课题组内部“已审核实验记录”的结构化知识组织、项目级权限约束下的 RAG 问答，以及普通 RAG 与图谱增强 RAG 的可追溯对照验证仍有进一步研究空间。因此，本文不以替代成熟 ELN/LIMS 为目标，而是在课题组电子实验笔记场景中构建可信知识闭环，并验证知识图谱增强检索在实验问答中的作用。

### 系统设计章节

建议强调：

- 借鉴 eLabFTW/SENAITE 的记录、权限、审批、审计思路。
- 借鉴 openBIS/LabKey 的项目化科研数据组织方式。
- 借鉴 Chemotion 的领域结构化模板思路。
- 借鉴 Dify/RAGFlow 的 RAG 流水线和应用编排思路。
- 本文实现的区别在于：围绕“项目级权限 + 审核可信语料 + 知识图谱增强 RAG + 实验对照评价”收束。

### 实验章节

建议将外部项目作为“系统设计来源”，而不是实验对手。实验对手应保持当前系统内部的两种模式：

| 对照模式 | 说明 |
| --- | --- |
| 普通 RAG | 仅基于项目资料/笔记向量检索生成回答 |
| 图谱增强 RAG | 在普通检索基础上加入实验实体关系、来源笔记和结果链路 |

这样更符合论文实验可控性，也避免将成熟平台拿来做不公平横向评测。

## 六、建议立即落地的三件事

1. 在论文第 2 章增加“成熟 ELN/LIMS 与 RAG 平台对比表”，使用本报告第二节。
2. 在第 6 章系统设计中增加“可信知识闭环设计依据”，引用 eLabFTW、SENAITE、openBIS、LabKey。
3. 在第 7 章实验中补齐人工盲评结果，并把冻结清单、日志 ID、语料哈希、模型版本作为实验复现证据。
