## 1. 研究问题、假设与可写结论

### 1.1 研究问题

- RQ1：在相同项目资料与相同问题下，一跳关系证据相对于文档混合检索是否改变答案要点的证据覆盖？
- RQ2：证据覆盖差异是否伴随同方向的独立人工事实准确性与可追溯性差异？该问题只分析关联，不把覆盖变化解释为因果中介。
- RQ3：关键词检索、文档混合检索、图关系上下文和文档—关系联合上下文在不同任务类型上的效果、失败机制、时延与 Token 成本边界是什么？`pure_llm` 仅作为无项目证据的校准基线，不用于回答检索策略边界。

### 1.2 预先指定的主要比较

主要比较为 `kg_enhanced_rag - project_rag`。两者使用相同的文档混合检索实现与生成模型；前者额外加入当前一跳图关系上下文。主要结局为问题级人工事实准确性差值。

关键次要结局为：

1. 问题级人工可追溯性差值；
2. 冻结答案要点的证据覆盖率差值；
3. 第 2.2 节四个理论分层中的描述性差值；
4. 项目分层的逐题 `Δ证据覆盖—Δ人工准确性/可追溯性` 四象限与 Spearman 秩相关，仅作描述性关联。

本设计允许检验“在本冻结任务集和当前实现中观察到差异”，不允许直接写成“一跳图谱普遍提高 RAG”“系统达到某事实准确率”或“跨领域泛化成立”。三个项目只能形成三个项目内的条件性估计与跨项目复制案例；即使方向一致，也只能称“三个冻结项目中观察到一致方向”，不能代表一般科研场景总体。

## 2. 研究对象与抽样单位

### 2.1 项目与问题

- 至少 3 个相互独立的真实项目；每个项目至少 20 题，总计至少 60 个唯一问题。
- 每题必须具有全局唯一 `question_id`，并同时记录 `project_id` 与项目内 `local_question_index`。不同项目中的本地序号可以相同，统计与归档不得只用 `question_index` 连接。
- 问题由未查看任何正式模型回答的外部命题者依据已审核记录编写；命题者身份、时间与未查看回答的声明进入冻结材料。
- 同一事实的同义改写不得跨开发集和测试集；近重复问题在冻结前由人工和文本相似度双重检查。
- 只允许一个有效主要批次。因预先定义的全局配置或工件漂移而失效的尝试必须完整隔离、归档，不得选取其中任何结果；失效判定不得基于答案质量。恢复原冻结条件并建立的新批次才可成为唯一有效主要批次。单案例技术失败保留在分母中，不能删除后补题。

### 2.2 问题类型

每题预先指定且只指定一个细分类别：

1. 资料事实型；
2. 单跳实验对象关系型；
3. 来源追溯型；
4. 全量集合与计数型；
5. 时间与实体约束型；
6. 跨关系连接/聚合型；
7. 无答案/应拒答型。

为避免用 7 个小样本格做不稳定排序，主要异质性描述合并为四个理论分层：

1. 事实与来源：资料事实型、来源追溯型；
2. 单跳关系：单跳实验对象关系型；
3. 约束与聚合：全量集合与计数型、时间与实体约束型、跨关系连接/聚合型；
4. 拒答：无答案/应拒答型。

不再机械要求七个细分类别各至少 8 题。冻结前报告真实候选池的类别分布；某理论分层只有在总题数至少 10 且覆盖至少 2 个项目时才生成方法差值图，否则只列逐题案例，不作类别排序。包含“这些、上述、前三项”等指代的问题必须改写为自包含问题；Rust 实验执行器固定传入 `history=None`，本批次不研究多轮对话。

### 2.3 分析单位与重复测量

- 主要分析单位是“问题”，项目是外部效度分层/聚类单位。
- 两名评价者的评分是同一答案的重复评价，不是两个独立样本。
- 模型的多次生成是同一问题—方法的重复测量，不得把重复次数当作新增问题数。
- 主要人评批次每个问题—方法只生成 1 个回答，以适配当前方法隐藏评价与配对分析；另行建立的 3 次生成稳定性批次只作次要/探索性分析，不进入主要人工结局，也不得替代 60 个唯一问题。

若研究者决定对 3 次生成全部做人评，必须在任何正式回答前发布 v3，预先定义重复层级、抽样和汇总方法，并修复当前盲评导出按 `(question_index, mode)` 判重的实现。不得在看到回答后挑选“最好的一次”。

## 3. 五种方法的操作性定义

所有生成调用使用同一个冻结的生成服务、模型标识和生产代码。生成主调用当前固定 `temperature=0.1`、`max_tokens=1800`；引用修复调用固定 `temperature=0.0`，最多 1 次。若冻结前代码事实发生变化，必须更新本节并建立新的协议版本。

| 方法 ID | 论文中的操作性名称 | 实际证据输入与行为 |
| --- | --- | --- |
| `pure_llm` | 无项目证据生成基线 | 不读取项目文档或图关系；使用专用纯模型提示，项目事实无法确认时应拒答。 |
| `bm25_rag` | BM25 文档检索 + 生成 | 只执行词项检索；不加入图关系；有项目活动块但零命中时可能触发查询改写。 |
| `project_rag` | 文档混合检索 + 生成 | 按冻结的 Rust 检索策略融合向量和词项候选；不加入图关系；零命中时可能触发查询改写。 |
| `structured_query` | 图关系上下文生成基线 | 不检索文档；检索一跳图关系。有关系时仍调用生成模型并要求 `[G编号]`，无关系或预算耗尽时由系统返回确定性拒答。 |
| `kg_enhanced_rag` | 文档混合检索 + 一跳图关系 + 生成 | 文档检索路径与 `project_rag` 相同，并额外加入一跳图关系上下文。 |

重要边界：当前 Rust `structured_query` **不是**旧协议所称的“零 Token、确定性直接数据库/图查询”。除无关系兜底外，它会进入提示构造和模型生成。正式论文必须使用上表名称和实际行为。若要研究确定性直接结构化查询，必须实现新的独立方法 ID、验证其不调用生成模型，并在运行前另行预注册；不能把当前模式事后改名为确定性查询。

### 3.1 生产回退属于方法的一部分

以下行为纳入各方法的整体效果，不在主要分析中事后排除：

- 文档零命中时的查询改写及补充检索；
- 引用审计失败后的单次引用修复；
- 图关系为空、上下文预算耗尽或证据不足时的系统拒答；
- 集合型问题采用更大的有效文档/图关系 top-k。

对适用文档检索的方法，每个案例必须显式记录 `query_rewritten`、补充查询数；对 `pure_llm` 和 `structured_query` 固定记录 `N/A`。所有方法显式记录 `repair_attempted` 或 `N/A`、回退原因、来源/关系数量和提示版本。另报告查询改写、引用修复和系统兜底的发生率与代表性病例，不进行大量小格的正式效应比较，也不得据此删除案例或重算“更好看”的主要效果。

## 4. 输入、金标准与外部冻结

### 4.1 每个项目的语料工件

每个项目保存并冻结：

- 已审核且同步成功的知识文档清单、原始文件 SHA-256、数据库文件 ID、审核状态和同步状态；
- Rust API 返回的活动文档语料 `corpus_snapshot_hash`、有效 chunk 数、`rag_index_version`、数据集 ID、嵌入模型；
- 活动图实体/关系快照的规范化 SHA-256、实体数、关系数和 `graph_schema_version`；
- 项目内用于回答每题的来源定位，精确到文档/块或图关系身份；
- 去标识化说明和数据使用授权/伦理边界。

文档快照哈希不能代替图快照哈希。`structured_query` 和 `kg_enhanced_rag` 使用图关系；若运行配置只冻结文档语料而未冻结实际图实体/关系集合，正式批次必须失败关闭。

### 4.2 问题与答案要点

`questions.json` 每题至少包含：

- `question_id`、`project_id`、`local_question_index`、题干；
- 主要问题类别和可选辅助标签；
- `answerable`；
- 对 `answerable=true` 的题：原子化 `gold_facts`、方法无关的 `reference_answer`，以及每个要点冻结的可接受文档块/图关系支持集；
- 对 `answerable=false` 的题：方法无关的拒答标准；此类题不得为了通过格式校验而虚构 `gold_facts`；
- 命题者身份代码与冻结时间。

答案要点、参考答案、支持集和拒答标准必须在查看正式回答前完成。检索证据覆盖率的可复算命中规则为：某 gold fact 的冻结支持 ID 集合与该方法返回的文档块/图关系 ID 集合相交。文本 alias 只能用于辅助审计或发现待复核候选，不能独立证明“证据支持该事实”。事实准确性与可追溯性由独立评价者分别依据方法无关参考与方法返回证据判断。

### 4.3 评价者

- 至少 2 名未参与系统开发、命题、gold 编写或参数调整的独立评价者。
- 评价者账号只能拥有评价权限，不能读取项目、管理项目或查看解盲日志。
- 两名评价者独立完成同一主要人评批次，期间不讨论具体案例。
- 分歧可由第三人复核，但保留两名原始评分；第三人结果不替换一致性统计。
- 评价者知情同意、利益冲突和完成签核进入归档；公开材料使用去标识化评价者代码。

## 5. 运行设计与随机化

### 5.1 分项目运行

Rust 创建端点单次最多接受 50 题，且一个实验运行绑定一个项目。因此至少建立 3 个项目内运行，每个运行包含该项目的全部冻结问题、五种方法和 `repetitions=1`。五方法全部保留自动证据覆盖、运行可靠性、时延与 Token 结果；主要两方法 `project_rag` 与 `kg_enhanced_rag` 对全部问题进行双人评价。其余三方法使用同一个、在首个正式回答前冻结的 `question_id` 子样本进行探索性双人评价；冻结材料必须给出 `n_sub`、项目/四理论分层配额、抽样种子和完整 ID 清单，该子样本不进入主要人工比较。最低 60 题时，主要人评工作量为 `60 × 2 方法 × 2 人 = 240` 份 item-rating，探索人评额外为 `n_sub × 3 方法 × 2 人`。各项目使用预先生成且冻结的随机种子；生产执行器根据种子对问题—方法顺序随机化。

跨项目汇总必须使用 `(project_id, question_id, mode)` 作为唯一案例键。当前单批次导出与汇总工具不足以合并多项目结果；在冻结前必须提供失败关闭的多项目合并器，核对每个项目的运行 ID、问题文本、五方法完整性、题集/语料/图快照哈希和评价者集合。合并产物必须显式保留 `source_project_id`、`source_run_id`、`source_batch_id`、全局 `question_id` 和项目内序号，禁止靠重新编号掩盖来源。

### 5.2 生成稳定性补充批次

主要人评批次完成并封存后，可按同一冻结输入另建 `repetitions=3` 的稳定性批次，报告自动证据覆盖、回答长度、Token、时延及失败率的批内变异。该补充批次：

- 不进入主要人工准确性或可追溯性估计；
- 不改变主要人评批次的答案或规则；
- 不得把 3 次重复计作 3 倍样本量；
- 与主要批次使用不同的运行 ID，并在论文中明确标为次要/探索性。

### 5.3 盲法

盲评页面隐藏方法、模型、原始日志 ID、运行顺序、文件名以及 `[S]`/`[G]` 来源类别，统一显示 `[E编号]`。为保证准确性测量效度，同一问题对所有方法显示完全相同、由外部命题者预先冻结且不含方法信息的参照物：`answerable=true` 显示方法无关的 `reference_answer`/gold-fact checklist；`answerable=false` 显示方法无关的拒答标准。前者用于判断事实正确性和完整性，后者用于判断拒答是否正确；二者均不得包含方法标签或方法自己的检索结果。方法返回的匿名证据只用于判断可追溯性。评价者仍可能从证据文本结构、有无证据或系统拒答措辞推测方法，因此本研究称为“方法标签隐藏”而不是保证完全双盲；论文必须披露这一限制。

当前盲评 UI/导出不提供上述方法无关参考，因此主要结局“人工事实准确性”当前尚不可测，正式冻结保持 `BLOCKED`。若最终不实现该参考，主要结局必须降名为“基于所示证据的回答可支持性”，且不得声称测得完整事实准确性。

## 6. 结局指标与计分规则

### 6.1 主要结局

人工事实准确性：按冻结的、与方法无关的 `reference_answer`/gold-fact checklist，由每位评价者对每个可评回答判断事实正确性与必要事实完整性，给出 `accurate/inaccurate`。问题—方法级得分为两位评价者二元值的平均数（0、0.5 或 1），主要估计量为 `kg_enhanced_rag - project_rag` 的问题内配对差值。技术失败不进入人工评分或 kappa，按第 7.2 节预定规则自动记为 0 并保留在主要分母。

### 6.2 关键次要结局

- 人工可追溯性：评价者只根据方法返回的匿名证据判断回答中的关键结论是否可追溯；两位评价者二元值平均后做问题内配对差值；
- 检索证据覆盖率：`answerable=true` 题中，冻结 gold fact 的支持 ID 集合与方法返回证据 ID 集合相交的要点比例；自动计算并保留逐要点交集记录；文本 alias 覆盖另列为辅助指标；
- 1–5 综合评分：只作有序描述和敏感性分析，不把均值差当作等距量表的唯一结论；
- 无答案题拒答正确率；
- 完整列举任务的精确完成率；
- 回答级引用语法通过率与人工证据支持判断；两者不得混写。

对 `answerable=false` 题，由准确性评价判断拒答是否符合冻结标准；它们不进入主要可追溯性差值。若回答额外提出项目事实，则另作安全性诊断，分母为“产生事实主张的无答案题回答”，不得跨方法解释为总体可追溯率。`pure_llm` 没有项目证据时不把空证据自动记为可追溯；在 `answerable=true` 题上拒答、空答或给出无证据项目事实均按主要可追溯性 0 处理。

### 6.3 资源与可靠性指标

- 端到端 `response_ms` 的中位数、P95 和完整分布；
- Prompt、Completion 和总 Token；外部服务可得时记录单题成本；
- 查询改写率、引用修复率、系统兜底率和运行失败率；
- 来源数量、图关系数量；若冻结前实现并定义明确的文档/图上下文 `truncated` 字段和分母，再报告上下文截断率，否则删除该指标。

服务端 `response_ms` 与外部计费记录的口径不同，必须分别命名。缺失 Token/成本不能按 0 处理。

## 7. 统计分析计划

### 7.1 主要估计

1. 主要分析从全部预定 `(project_id, question_id, mode)` 案例开始；可评回答取两评价者均值，单案例技术失败取预定 0。其余三方法的人工评分只进入预先冻结共同子样本的探索性附表。
2. 对每个冻结问题计算 `kg_enhanced_rag - project_rag` 准确性差值；一方技术失败时用该方 0 与另一方得分配对，双方失败时差值为 0。
3. 每个项目内对问题差值取平均，再对项目均值等权平均，避免项目题量差异主导总体结果。
4. 同时报告每个项目的原始分子/分母、均值差、中位差、胜/平/负题数和全部逐题配对值。
5. 问题层 95% bootstrap 区间按项目分层、在各项目内重采样问题，再按项目等权汇总；随机种子和迭代次数在 `analysis-config.json` 中预先冻结。由于项目数只有最低 3 个，该区间描述冻结项目集合内的问题抽样不确定性，不作为项目总体的稳定 cluster-bootstrap 推断。

只有 3 个项目时，不进行项目随机效应或项目总体的推断性声称。因此项目分层原始结果、配对效应量和胜/平/负题数是主要解释依据，不以 `p < 0.05` 或单一置信区间作为结论开关，也不声称代表所有科研项目。

### 7.2 次要比较与多重性

- 主要可追溯性比较固定限于 `answerable=true` 的全部冻结问题：有实质回答由人评，拒答、空答或单案例技术失败记 0；`answerable=false` 只进入拒答正确率和安全性诊断，不进入主要可追溯性配对。
- 检索证据覆盖及 RQ2 的 `Δ覆盖—Δ人工结果` 描述固定限于 `answerable=true`、两主要方法均有定义的 gold 支持集；关联分析中的准确性也取同一子集，不与全部问题的主要准确性估计混写。
- 五方法的自动证据覆盖与资源指标均按冻结题集报告；其余三方法的人评只在预先冻结子样本中作探索性描述，不进行确认性显著性检验，也不与主要全量比较混写。
- 问题类别分析预先指定为异质性描述；类别内样本量较小时只报告原始结果和区间，不作“某方法最适合某类”的确定性排序。
- 两位评价者的准确性和可追溯性分别报告一致率与 Cohen's kappa；1–5 分报告加权 kappa。kappa 不能替代原始一致率。
- 技术失败采用唯一预定口径：准确性在全部冻结问题中记 0；主要可追溯性仅对 `answerable=true` 题记 0；`answerable=false` 题在拒答正确率中记 0、可追溯性记 `N/A`。自动编码案例不交给人工评价，也不进入一致率/kappa；另行报告技术失败率与原因。不得只分析成功回答，也不得因失败替换问题。若失败源于全局配置/工件漂移而非单案例服务错误，则整批失败，不适用逐案例记 0，必须按第 2.1 节隔离旧尝试并建立新批次。

五个分母固定如下：

1. 准确性：两主要方法 × 全部冻结问题，单案例技术失败记 0；
2. 主要可追溯性：两主要方法 × 全部 `answerable=true` 问题，拒答/空答/技术失败记 0；
3. 拒答正确率：两主要方法 × 全部 `answerable=false` 问题，技术失败记 0；
4. 检索证据覆盖：`answerable=true` 问题的全部冻结 gold facts；
5. kappa/一致率按结局分别固定：准确性一致率/kappa 的分母是实际交给两名评价者且两人均完成准确性判断的全部可评回答；可追溯性一致率/kappa 的分母是实际交给两名评价者且两人均完成可追溯性判断的 `answerable=true` 可评回答。自动编码技术失败均排除；主要矩阵与探索矩阵分别报告，不得合并分母。

### 7.3 样本量依据

当前“3 项目、每项目 20 题”是最低设计规模，不是已经完成的功效论证。冻结前在不查看正式答案的条件下补充精度/情景敏感性表，展示不同配对相关性、真实差值和失败率假设下的区间宽度与可识别范围；该表用于解释设计限制和必要时增加问题数，不得据此把 3 项目、60 题包装成“统计功效充分”。脚本、参数和输出进入冻结清单。

## 8. 失败归因

每个不准确、不可追溯、拒答错误或运行失败案例可有多个预先定义标签，但必须保留主要标签：

- 语料中无答案或 gold 错误；
- 文档检索未覆盖必要事实；
- 图关系未覆盖必要事实；
- top-k/上下文预算截断；
- 查询改写无效或引入偏移；
- 词项/实体/时间解析错误；
- 结构化过滤错误；
- 连接/聚合能力缺失；
- 证据完整但生成遗漏；
- 生成引入无证据事实；
- 引用编号正确但内容不支持结论；
- 接口、外部模型或运行时失败；
- 评价规则不充分。

先由方法标签隐藏的评价者记录不依赖检索日志的可观察症状；准确性/可追溯性评价封存并解盲后，再由技术复核者查看检索与运行日志编码可能机制。原因字段必须保存编码人、依据和置信度，并标记为解释性机制归因；因果性不确定时标为 `UNKNOWN`，不能把日志共现直接写成因果证明。

## 11. 完成标准与允许表述

只有同时满足下列条件，主要结果才可写为 Rust 冻结任务集上的预注册比较：

- 文档快照和图快照均与每个运行绑定；
- 冻结的主要 human-rating matrix 完整：两主要方法的全部可评回答由同两名独立评价者完成方法标签隐藏评价，技术失败按预定规则自动编码；五个分析分母与第 7.2 节一致；
- 失败、缺失和未执行案例全部保留；
- 多项目合并、证据包、引用、评分和统计脚本全部通过独立审计；
- 当前工作树、应用 revision、镜像、模型、参数、提示和代码均可回放；
- 结果解释遵守第 1 节和第 7 节的效应量、区间与外部效度边界。

若主要 matrix 不完整，主要人工结论不得报告。三种探索方法的共同子样本 matrix 若不完整，则整个探索性人评板块不报告，但不否定已完整的主要两方法比较；不得只保留探索子样本中的成功方法或案例。

即使上述条件全部通过，也只能说“在冻结的三个（或更多）项目与题集上观察到……”。这属于对冻结任务集的预注册条件性比较和三个项目的复制性描述；除非另有更大外部样本，不得写“适用于所有科研项目”或“具有普遍显著优势”。

## 13. 冻结与验证流程（待阻断项清零后执行）

1. 外部命题者交付项目语料、问题和 gold；研究者只做格式/来源完整性检查，不查看任何正式回答。
2. 运行多项目研究冻结验证器，要求项目数、唯一问题数、类别分布、评价者权限、文件哈希、文档/图快照和方法定义全部通过。
3. 形成干净 Git revision，构建镜像并记录 digest；用该镜像在每个项目重新核对 API 快照。
4. 生成只追加冻结清单，记录 v2、数据、代码、模型、参数、统计计划和随机种子。
5. 在首个回答前验证清单；失败即停止。
6. 分项目执行主要人评批次，保存原始 v1 证据包并独立审计。
7. 两名评价者完成冻结 human-rating matrix 中全部可评案例后解盲：主要两方法覆盖全部冻结问题，其余三方法仅覆盖冻结共同子样本，技术失败自动编码且不送评。主要 matrix 的任何未完成、重复评分、评价者集合漂移或权限越界都失败关闭；探索 matrix 不完整则按第 11 节整体取消该探索板块。
8. 多项目合并器核对来源运行与全局案例键，再运行冻结的统计脚本。
9. 先归档原始数据、门禁和统计 JSON，再生成论文表图与文字。

拟议目录和命令只能在对应文件真实存在后补充。当前不得用空模板、占位哈希或内部开发题集生成看似正式的 v2 manifest。
