## 已复现问题（按处理优先级）

### R01 · P1（条件性）：切换项目后，Agent 继续复用旧项目会话

定位：[AgentAssistant.tsx:345](/Users/yusong/Downloads/new/full-system/frontend/src/components/shared/AgentAssistant.tsx:345)。项目切换会清空会话引用，但创建会话的在途请求没有失效；旧响应随后将 session-A 写回共享组件。后端按 session 的 `project_id` 执行工具，见 [agent_runtime.rs:282](/Users/yusong/Downloads/new/full-system/backend/src/api/agent_runtime.rs:282)。

复现：延迟项目 A 的首次会话创建，切换到 B 后放行响应；在 B 再发指令，仍使用 session-A。实际前端源码受控执行记录两次 turn 都发往 session-A，界面项目均为 2。没有实际写入错项目；结论是指令路由已错，后续写操作存在落在 A 的风险。前提为启用新 Agent，示例配置默认关闭该功能。

最小修复：以项目和用户身份世代绑定会话、计划、turn 响应；切换后丢弃旧请求结果及确认闭包。回归应覆盖在途创建、在途 turn、待确认期间切项目。

### R02 · P2：重新校对 OCR 后，检索仍使用旧文本

定位：[rag/mod.rs:494](/Users/yusong/Downloads/new/full-system/backend/src/api/rag/mod.rs:494)，关联 [ocr.rs:304](/Users/yusong/Downloads/new/full-system/backend/src/api/ocr.rs:304)。入库判重只绑定原图片文件 hash、数据集和索引版本，没有绑定已确认 OCR 的版本或校对文本 hash。

真实 HTTP 复现：同一图片第一次提取并确认“20 C”成功入库；再次提取、确认“80 C”均成功，最新 OCR 返回“80 C”，数据库 chunks 仍为“20 C”。手动同步返回 200，文件还显示 `synced`，文本仍未更新。

最小修复：OCR 来源版本/文本 hash 进入索引身份；确认新结果时使旧同步记录失效并刷新 chunks。回归同时核对最新校对文本、检索内容、同步状态和文档快照。

### R03 · P2：MCP 资源列得出，但笔记和资料读不出

定位：[mcp.rs:1311](/Users/yusong/Downloads/new/full-system/backend/src/api/mcp.rs:1311)、[mcp.rs:1313](/Users/yusong/Downloads/new/full-system/backend/src/api/mcp.rs:1313)。笔记资源查询从 `experiment_notes` 取不存在的 `content_json`，内容实际在 `note_versions`；资料资源查询从 `files` 取不存在的 `metadata_json`。

真实 JSON-RPC 复现：`resources/list` 正常返回已批准笔记和图片资料 URI；逐一 `resources/read` 均为 HTTP 200、JSON-RPC 错误 `-32603`，分别提示上述列不存在。因此只看 HTTP 状态会漏掉失败。

最小修复：笔记连接当前版本读取正文；资料按现有字段构造响应。增加 list→read 的完整链路验证，检查 JSON-RPC result/error。

### R04 · P2：同轮多个确认动作，处理首项后其余项无法批准

定位：[agent_runtime.rs:1136](/Users/yusong/Downloads/new/full-system/backend/src/api/agent_runtime.rs:1136)、[agent_runtime.rs:1147](/Users/yusong/Downloads/new/full-system/backend/src/api/agent_runtime.rs:1147)。首项批准无条件完成整个 turn 并清空 `active_turn`，后续批准却依赖该活动 turn。

最小修复：动作绑定来源 turn；同一事务中处理单项，只有该轮全部动作终结后才完成会话。回归至少覆盖批准/批准和拒绝/批准。

## 两项高优先级静态风险（未动态验证）

**S01：既有 Agent 会话继续使用时，没有重验项目访问与敏感策略。** [agent_runtime.rs:165](/Users/yusong/Downloads/new/full-system/backend/src/api/agent_runtime.rs:165) 只在创建 session 时检查；create-turn 在 282 行只按会话所有者取项目，deep 生成计划及 fast 的 681 行模型调用没有相同检查，start-turn 的 449 行入口也未补查。若会话创建后项目变敏感或权限撤销，当前文本仍可能进入模型请求。工具各自的授权能限制工具读取，不能代替模型调用入口检查；本轮没有证明撤权后还能读取数据库正文。建议每个模型请求入口重验当前项目及策略。

**S02：外部 embedding 未纳入敏感项目策略。** [rag/mod.rs:643](/Users/yusong/Downloads/new/full-system/backend/src/api/rag/mod.rs:643) 声称 retrieval-only 不联系外部 AI；非 BM25 实际进入 [retrieval.rs:116](/Users/yusong/Downloads/new/full-system/backend/src/rag/retrieval.rs:116) 的 query embedding。MCP 的 [mcp.rs:1497](/Users/yusong/Downloads/new/full-system/backend/src/api/mcp.rs:1497) 及资料入库的 [index.rs:96](/Users/yusong/Downloads/new/full-system/backend/src/rag/index.rs:96) 也调用 embedding。[embedding.rs:77](/Users/yusong/Downloads/new/full-system/backend/src/embedding.rs:77) 支持 `openai_compatible`，83 行将 input 原文 POST 到配置 URL，而这些链路未见敏感项目外发检查。前提为配置外部服务；默认 hash 或本机服务不能据此认定实际外发。本轮没有读取真实 `.env` 或发出外部请求。建议统一区分本地/外部 embedding，在共享入库、检索边界执行策略，保留本地 BM25。

两项风险均有明确静态调用链，但部署前提及动态结果未核验；不计入上述 10 项已复现问题。
