# Anti-Defensive Writing(学术发布会原则)

## 核心规则

正面推进主张。写本文主张什么、证据表明什么、方法做到了什么;不要默认去解释本文不主张、不证明、不覆盖什么。
以平静、胜任的作者姿态写作:作者是在向读者解释论证,不是在与想象中的评审谈判。

## 保留必要的精确性

以下限制是**必要的**,保留且只说一次,放在合适章节(方法/讨论/局限):
- 影响主张有效性的(如答案规则事后建立、盲评未签核);
- 影响证据解释的(如 legacy 批次与交付系统的运行时差异);
- 影响适用范围的(如空载语料条件、单项目封闭语料);
- 影响研究设计的(如实验 5 的 paper_ready=false)。

写在正确的位置一次就够:**不散落在摘要、引言、贡献段、主题句和结论里重复**——除非该限制对该句本身必不可少。

## 检查清单(定稿前逐条过)

- 不必要的免责声明;
- 重复声明本文"不做什么";
- 过度对冲(仅/仍/尚未 连用);
- 高影响力位置(摘要、贡献句、结论段)出现限定语;
- 以限制开头的段落;
- 负面框架能改正面框架的;
- 仅为防止假想误解而加的解释;
- 自我削弱的贡献陈述("只是工程实现""不扩展表述为");
- 多余的"然而/不过/尽管"转折;
- "不是 X 而是 Y"结构滥用(每千字 ≤1 处为宜)。

凡削弱文本而不提升准确性的表述,一律修订。

## 修订程序

1. 给每个防御句定性:不必要的免责 / 必要的范围条件 / 真实方法学局限 / 有用的概念对比 / 基于证据的限定 / 冗余澄清。
2. 不必要的免责——删除。
3. 必要的范围条件——压缩为最短形式,合并到它首次出现的位置,后续以"见 7.1 节"式交叉引用代替重复。
4. 真实局限——一次说清,语气平静(用"适用范围为"而非"遗憾的是")。
5. 消极框架改积极框架:把"未能证明泛化"改写为"本文结论的适用范围是机制诊断"。

## 中文学术语替换对照

| 防御性写法 | 改法 |
| --- | --- |
| "不作为……的证明,也不作为……" | "本文结论的适用范围是……"(一次) |
| "仅作描述性参考" | "该结果为描述性结果"(首次)+ 后续省略 |
| "尚未……尚未……尚未……" 连用 | 合并为一句状态陈述 |
| "存在一定不足/明显不足" | "适用边界为 X"(具体化) |
| "本文不声称/不宣称/不外推" | 首次边界声明处保留一次,其余删除 |
| "这把结果定位为可行性证据,不作为优势证明" | "这组结果的证据定位是机制诊断" |

## 红线(与本项目并线约定一致)

- 不得删除或弱化:证据等级事实(paper_ready=false、事后规则、盲评未签核、legacy 批次)——这些是诚实性支柱,只能在**位置和次数**上收敛,不得改变事实与等级;
- 不动数字、公式、引文编号;
- 修改须可经 git diff 审计,逐处可回退。
